# miniprogram-sdk 项目说明与架构

本文档说明微信小程序版 XmovAvatar SDK（miniprogram-sdk）的职责、与 Web SDK 的复用关系、针对微信小程序的改造点，以及当前未解决的问题。

---

## 一、项目概述

**miniprogram-sdk**（包名 `@xmov/avatar-miniprogram`）是 **XmovAvatar 数字人 SDK 的微信小程序版本**，在微信小程序环境中实现与 Web 版对齐的数字人会话、通信与渲染能力。

### 1.1 主要能力

| 能力 | 说明 |
|------|------|
| **会话与通信** | `start_session` / `stop_session`（与 Web 同一套网关接口）；TTSA WebSocket（Socket.IO 协议）；`send_text` 上行；`tts_audio` / `face_data` / `body_data` 下行事件 |
| **数字人渲染** | 身体视频渲染（BodyRendererMP）、口型/脸部融合（AvatarRendererMP + GLPipelineMP）、帧调度（RenderSchedulerMP）、数据缓存（DataCacheQueueMP） |
| **资源与解码** | 使用 `wx.downloadFile` 拉取资源；msgpack/protobuf 解码 face/body；TTS 音频通过 InnerAudioContext 播放 |

### 1.2 对外 API

主入口为 **`XmovAvatarMP`**，提供：

- **生命周期**：`init()`、`start()`、`pause()`、`stop()`、`destroy()`、`getStatus()`
- **驱动**：`speak(ssml)`、`sendText(text, options)`（上行 TTS 文本）
- **回调**：`onMessage`、`onStatusChange`、`onTtsaReady`、`onTtsAudio`、`onFaceData`、`onBodyData`
- **依赖注入**：初始化时传入 `gatewayServer`、`appId`、`appSecret`、`gl`、`canvas` 等

## 二、如何复用 Web SDK

小程序端**并非**把整份 Web SDK 打包进来，而是采用「类型 + Proto 复用 + 构建时桥接 + 渲染/IO 在小程序侧重写」的策略。

### 2.1 类型复用

从仓库根目录的 Web SDK 直接引用类型定义：

- `miniprogram-sdk/src/types/index.ts` → `../../../src/types/index`（如 `AvatarStatus`、`RenderState`）
- `miniprogram-sdk/src/types/interfaces.ts` → `../../../src/types/frame-data`（如 `IRawFrameData`、`IRawBodyFrameData` 等）

构建时 Rollup 的解析根目录为仓库根，因此会正确解析到根目录下的 `src`。

### 2.2 Proto 复用

- **protobuf 运行时**：`proto-init.ts` 中 `import * as protobufNs from '../../src/proto/protobuf.min.js'`，直接使用 Web SDK 的 protobuf 库。
- **face_data schema**：`face_data_pb.js` 不在源码中 import，而是在 **build-heavy-rollup.js** 里通过 `injectFaceDataPb` 插件在编译期注入到 `proto-init` 的 `executeFaceDataPb()` 中，避免被 tree-shake 掉。

即：Protobuf 运行时和 face_data 的 schema 均来自 Web SDK 的 proto 目录。

### 2.3 构建时 Alias 桥接

以下模块在构建时被替换为小程序适配实现，**不**打包 Web 的实现：

| Web 模块 / 路径 | 替换为（miniprogram-sdk 内） |
|----------------|------------------------------|
| `socket.io-client` | `src/utils/socket-io-adapter.ts`（内部再使用 `adapters/websocket`） |
| `../utils/request`、`./utils/request`、`../../utils/request` | `src/utils/request-adapter-wrapper.ts`（内部用 `wx.request`） |
| `./AudioWorklet`、`baseRender/AudioWorklet`、`../baseRender/AudioWorklet` | `src/adapters/audio-worklet-adapter.ts`（小程序无 Worklet，空实现或降级） |

### 2.4 渲染与数据流不复用

Web 的 `GLPipeline`、`GLDevice`、`DataInterface` 等**没有**被打进小程序包，而是在 miniprogram-sdk 内单独实现：

- `GLPipelineMP`、`GLDeviceMP`、`DataInterfaceMP`：小程序版 WebGL 管线与数据结构
- `BodyRendererMP`、`AvatarRendererMP`、`RenderSchedulerMP`、`DataCacheQueueMP`、`ResourceManagerMP`：资源、身体渲染、脸部融合、帧调度、缓存等

这样做的原因：小程序无 Worker、Canvas/WebGL API 有差异、单文件体积限制，需要专门适配。

## 三、Canvas/WebGL 差异与「重写」而非「适配器+桥接」的原因

最初设想是：**通过模块适配器 + 构建时桥接，尽量不改 Web SDK 代码、尽量复用 Web SDK**。实际落地方案是：**类型与 Proto 复用，渲染与数据流在小程序侧几乎全部重写**（GLPipelineMP、GLDeviceMP、DataInterfaceMP、BodyRendererMP、AvatarRendererMP、RenderSchedulerMP、DataCacheQueueMP、ResourceManagerMP 等）。本节说明 Canvas/WebGL 与运行环境的真实差异，以及为何会走向「重写」而非「适配器复用」。

### 3.1 Canvas / WebGL / 运行环境差异（简要）

| 能力 | Web SDK 用法 | 微信小程序差异 |
|------|--------------|----------------|
| **Canvas 对象** | `HTMLCanvasElement`，同步 `canvas.getContext('webgl2')` | 无 DOM，Canvas 通过 `createSelectorQuery().select('#id').node()` 异步拿到，类型是 `WechatMiniprogram.Canvas`，不是 `HTMLCanvasElement`。 |
| **WebGL 上下文** | 在 GLDevice 内部 `this.canvas.getContext('webgl2', opts)` | 小程序侧通常由页面/组件先拿到 canvas 再 `getContext('webgl2')` 或 `webgl`，且可能只支持 WebGL1，需外部传入 `gl`。 |
| **渲染循环** | `window.requestAnimationFrame(cb)` 或 `HTMLVideoElement.requestVideoFrameCallback(cb)` | 无 `window`；`requestAnimationFrame` 挂在 **canvas 对象** 上（`canvas.requestAnimationFrame`），需在拿到 canvas 后 polyfill 到 `globalThis`。 |
| **视频与纹理** | `HTMLVideoElement`、`HTMLImageElement`、`ImageBitmap`（含 `createImageBitmap`、`.close()`） | 无 `<video>`/`<img>`；视频解码走 `VideoDecoder` 或自定义解码，帧数据多为 `ArrayBuffer`/`ArrayBufferView`，用 `gl.texImage2D` 传 raw buffer；`wx.createImageBitmap` 能力有限且存在兼容问题。 |
| **ImageBitmap** | `DataCacheQueue` 以 `ImageBitmap` 为 body/face 帧缓存，`_getBodyImageBitmap` / `_getFaceImageBitmap` 等返回 ImageBitmap，渲染前 `frame.close()` | 小程序无标准 `createImageBitmap` 或仅部分支持，文档/代码注明「ImageBitmap 单点测试有问题」，难以直接复用「ImageBitmap 进缓存」的整条链路。 |
| **Worker** | `decoder.ts` 用 `new Worker(workerURL)` 在 Worker 里解码视频，结果回传主线程 | 小程序**不支持 Worker**，解码只能主线程或通过其他方式（如 VideoDecoder 主线程解码）。 |
| **DOM / Window** | `document.createElement`、`document.getElementById`、`document.body`、`document.addEventListener`、`document.hidden`；`window.addEventListener`、`window.setTimeout`、`window.setInterval`、`performance.now()`；`window.URL.createObjectURL`、`window.AudioContext` 等 | 小程序无 `document`、无 `window`，只能通过 polyfill 或适配器提供「形似」的接口，且很多 Web 模块**直接写死**了 `document.xxx` / `window.xxx`。 |
| **WebGL 扩展与格式** | Web 版 GLDevice 假定 WebGL2，使用 `HALF_FLOAT`、部分 internalFormat（如 R16F、RGB10_A2 等） | 小程序可能只有 WebGL1，需在运行时判断 `gl.texImage3D` 等区分 WebGL2/1，部分格式需注释或降级（GLDeviceMP 中有对应处理）。 |
| **上下文事件** | `canvas.addEventListener('webglcontextlost'/'webglcontextrestored')` | 小程序 canvas 实例的接口与 DOM 不一定一致，事件绑定方式可能不同。 |

以上差异表明：Web SDK 从 **Canvas 创建、上下文获取、渲染驱动、视频/图像来源、缓存数据结构（ImageBitmap）、解码线程（Worker）到全局环境（document/window）** 都直接依赖浏览器 API，而不是依赖一层「平台抽象接口」。

### 3.2 为何最终是「重写」而非「适配器 + 桥接复用」

- **Web SDK 未做平台抽象**：核心渲染与数据流直接依赖具体类型和全局对象，例如：
  - **GLDevice**：构造函数接收 `HTMLCanvasElement`，内部 `canvas.getContext('webgl2')`，`run()` 里用 `requestAnimationFrame` 或 `syncMedia.requestVideoFrameCallback(syncMedia: HTMLVideoElement)`。
  - **GLPipeline**：`renderBackground(background: HTMLImageElement | HTMLVideoElement, char_body: ...)`，`setSyncMedia(syncMedia?: HTMLVideoElement)`，纹理来源为 `ImageBitmap | HTMLImageElement | HTMLVideoElement`；并直接使用 `(window as any).avatarSDKLogger`、`performanceConstant`、`performanceTracker.markEnd`。
  - **DataCacheQueue**：body/face 帧以 **ImageBitmap** 存并对外暴露 `_getBodyImageBitmap` / `_getFaceImageBitmap` / `_getRealFaceImageBitmap`，且内部调用 `frame.close()`；构造函数里 `window["__dev_event_queue__"] = ...`。
  - **decoder**：强依赖 `Worker`，`new Worker(workerURL)` 做视频解码，解码结果再通过 ImageBitmap/帧对象回写到 DataCacheQueue。
  - **AvatarRenderer / index**：`document.createElement("canvas")`、`document.getElementById`、`document.body`、`window.addEventListener`、`document.addEventListener`、`document.hidden`、`window.setInterval` 等遍布多处。

  要在小程序侧「只做适配器 + 构建时桥接、尽量不改 Web SDK」就要求：**所有上述能力都通过可注入的抽象（如 ICanvas、IGLContext、IAnimationLoop、IVideoSource、IImageSource、IWorkerPool）提供**，且 Web SDK 只依赖这些接口而不直接写死 DOM/Worker/ImageBitmap。当前 Web SDK 并非如此设计，因此无法在不改 Web 代码的前提下，仅靠「换实现」就复用到小程序。

- **数据流与类型强绑定**：Web 的「视频解码 → ImageBitmap/帧 → DataCacheQueue → AvatarRenderer/GLPipeline」整条链路是围绕 **ImageBitmap + HTMLVideoElement** 设计的。小程序没有等价物，且 ImageBitmap 在小程序上不稳定。若坚持复用 Web 的 DataCacheQueue / AvatarRenderer，就需要在 Web SDK 里把「帧」抽象成接口（例如「可上传到 GL 的纹理源 + 尺寸 + dispose」），再由小程序实现该接口（如包装 ArrayBuffer + texImage2D）。这属于对 Web SDK 的**结构性重构**，而不是「加一层适配器」就能完成。

- **工期与风险**：在「不改 Web SDK」的约束下，唯一可行路径是：在小程序侧用**与 Web 相同的业务逻辑、但面向小程序 API 的实现**（即 GL*MP、*RendererMP、*CacheQueueMP 等）。这样无需动 Web 主仓、不影响 Web 稳定性，但会形成**两套渲染与数据流实现**，即当前状态。

### 3.3 若要坚持「适配器 + 桥接、尽量复用 Web SDK」需要什么

要真正按原架构「尽量不改 Web SDK、通过适配器复用」，需要：

1. **在 Web SDK 中引入平台抽象层**（而不是在 miniprogram 里再包一层）：
   - **ICanvas / IGLContext**：创建与获取 WebGL 上下文、尺寸、contextlost/restore 事件，由调用方注入（Web 注入 DOM Canvas，小程序注入适配器封装）。
   - **IAnimationLoop**：`requestAnimationFrame` / `requestVideoFrameCallback` 的抽象，Web 用 window/video，小程序用 canvas.requestAnimationFrame 或 polyfill。
   - **IVideoSource / IImageSource**：视频或单帧图像的抽象（如 `getFrame(time)` → 可上传到 GL 的源），Web 用 HTMLVideoElement/ImageBitmap，小程序用 VideoDecoder 输出 + ArrayBuffer/texImage2D。
   - **IDataCacheQueue**：帧缓存接口，不暴露 ImageBitmap，而是暴露「纹理源 + 元数据」（或上传到 GL 的句柄），这样 Web 用 ImageBitmap 实现该接口，小程序用 raw buffer + 纹理实现。
   - **IWorkerPool / IDecoder**：解码任务抽象，Web 用 Worker，小程序用主线程或单线程队列，实现同一接口。

2. **Web SDK 重构为依赖上述接口**：  
   GLDevice、GLPipeline、DataCacheQueue、decoder、AvatarRenderer、RenderScheduler 等只依赖接口类型，不直接使用 `HTMLCanvasElement`、`HTMLVideoElement`、`ImageBitmap`、`Worker`、`window`、`document`。构造函数或工厂由上层传入「平台实现」（Web 包传入 DOM/Worker 实现，小程序包传入 wx/Canvas/主线程解码实现）。

3. **构建与打包**：  
   小程序构建时，通过 alias 或条件导出，将上述接口的**小程序实现**打进同一套 Web SDK 业务代码，这样业务逻辑只有一份，差异仅在「谁实现了 ICanvas/IGLContext/IDataCacheQueue/…」。  
   当前未做第 1、2 步，因此第 3 步无法成立，只能退化为「类型 + Proto 复用 + 少量 request/socket/audio 桥接，渲染与数据流在 miniprogram 内重写」。

## 四、针对微信小程序的改造

### 4.1 构建与运行环境

- **Rollup 单包 UMD**：`build-heavy-rollup.js` 产出 `xmov-avatar-mp.heavy.js`（UMD），满足小程序对单文件体积的要求；通过 `replaceGlobals` 做全局替换：
  - `window` → `globalThis`
  - `document` → `getDocument()`
  - `navigator` → `__navigator`
  - `new Worker(...)` → `createWorkerAdapter()`（空实现，因小程序不支持 Worker）
- **Polyfill**：
  - **window-polyfill**：`window` 指向 `globalThis`，并将 **Canvas 的 requestAnimationFrame**（或 setTimeout 降级）挂到 `globalThis.requestAnimationFrame`，供渲染循环使用。
  - **api-polyfill**：提供 `fetch`、`Event`、`Image`、`URL`、`ImageBitmap`、`Blob` 等；**module-polyfill** 暴露与 Socket.IO 兼容的 `io`。

### 4.2 适配器（替换 Web 能力）

| 适配器 | 说明 |
|--------|------|
| **Canvas** | `createCanvasAdapter`：通过 `canvasId` + `componentInstance` 用 `wx.createSelectorQuery` 取节点，再 `getContext('webgl2')` / 降级 `webgl`，封装成与 Web 类似的「取节点 + 拿 gl」的用法。 |
| **网络** | `mpRequest` + `request-adapter-wrapper`：用 `wx.request` 发请求；签名逻辑与 Web 的 `headersNeedSign` 一致。 |
| **WebSocket** | `adapters/websocket`：实现 Engine.IO 协议，对外提供与 Socket.IO 兼容的 `io()`，用于 TTSA 连接。 |
| **音频** | `AudioAdapter`：封装 `wx.createInnerAudioContext()`，提供 `src`、`play`、`pause`、`volume`、事件等；TTS 音频为 ArrayBuffer 时先 `wx.getFileSystemManager().writeFileSync` 写到临时文件再设 `src` 播放。 |

### 4.3 WebGL 能力检测

通过 `GLDeviceMP.getWebGLCapabilities(gl)` 在运行时检测实际支持的 WebGL 特性，输出格式如下：

```json
{
  "isWebGL2": true,           // 是否支持 WebGL2
  "support3DTexture": true,   // 是否支持 3D 纹理 (LUT 需要)
  "supportFloatTexture": false, // 是否支持浮点纹理 (OES_texture_float)
  "supportFloatVertex": true,  // 是否支持浮点顶点
  "supportVAO": true,          // 是否支持 VAO
  "supportInstancedArrays": true, // 是否支持实例化
  "supportDepthTexture": true  // 是否支持深度纹理
}
```

**真机实测结果（iOS/Android）**：

| 特性 | iOS | Android | 说明 |
|-----|-----|---------|------|
| WebGL2 | ✅ | ✅ | 完整支持 |
| 3D 纹理 | ✅ | ✅ | LUT 可用 |
| Float 纹理 | ❌ | ❌ | `OES_texture_float` 不支持 |
| Float 顶点 | ✅ | ✅ | - |
| VAO | ✅ | ✅ | - |
| 实例化 | ✅ | ✅ | - |
| 深度纹理 | ✅ | ✅ | - |

**影响评估**：
- **LUT (3D 纹理)**：✅ 可用，但需代码适配（GLPipelineMP 已有 sampler3D）
- **BlendShape (Float 纹理)**：❌ 不支持 → **脸部变形无法生效**，这是当前脸部不动的根本原因
- **PCA 权重**：同样使用 Float 纹理，可能受影响

### 4.4 渲染与资源

- **GLPipelineMP**：相对 Web 版 `GLPipeline` 去掉对 `performanceConstant` 的依赖，shader 中增加注释说明「小程序视频解码出来的数据/UV 可能需翻转」；其余管线逻辑与 Web 对齐（背景、mesh、blendshape、骨骼等）。
- **GLDeviceMP / DataInterfaceMP**：小程序版 WebGL 封装与数据结构，供 AvatarRendererMP、身体渲染等使用。
- **ResourceManagerMP**：使用 `wx.downloadFile` 下载资源（含 `face_ani_char_data`、body 资源等），支持进度回调；提供 `wxDownloadToTempFile`、`wxDownloadToArrayBuffer`，供解码与纹理使用。
- **BodyRendererMP**：使用小程序 Canvas 的 `requestAnimationFrame`（或全局 polyfill）驱动循环；无 Worker，解码与渲染在同一线程。

### 4.4 业务逻辑与协议

- **会话**：与 Web 一致，调用同一套 `start_session` / `stop_session` 接口（签名、payload 结构一致），拿到 `socket_io_url`、`token`、`room`、`resource_pack` 后再建 TTSA 连接。
- **TTSA**：`enter_room`、`first_start_timestamp`、`state_change`、`send_text`，以及 `face_data` / `body_data` / `tts_audio` 的解析与投递到 RenderScheduler / AvatarRenderer / AudioAdapter。
- **口型与脸**：`FaceSignalAdapter`、`LipSyncControllerMP`，沿用 Web 的 `lipsync-core`（如 `clamp01`、`mapBlendshapeGroups` 等）；脸部 LUT 在 `AvatarRendererMP` 中标注为「小程序暂不支持 LUT」。

### 5.1 微信小程序 WebGL 要求：必须使用 WebGL2

**项目要求**：小程序 SDK **必须使用 WebGL2**，不提供 WebGL1 降级。原因包括：

- 渲染管线（GLPipelineMP）的 shader 全部为 `#version 300 es`（GLSL ES 3.0），仅 WebGL2 可编译。
- LBS（骨骼蒙皮）、PCA、blendshape 等依赖的 uniform/attribute 与纹理用法按 WebGL2 编写。
- LUT（3D 纹理）依赖 `texImage3D` / `TEXTURE_3D`，为 WebGL2 独有；若环境支持 WebGL2，LUT 可启用。

因此：**仅当 `canvas.getContext('webgl2')` 成功时 SDK 才可正常运行**；若运行环境只支持 WebGL1，应提示用户升级微信或更换设备，而不是回退到 webgl。

| 能力 | 说明 | 在「必须 WebGL2」前提下的结论 |
|------|------|-------------------------------|
| **LUT（3D 纹理）** | `gl.TEXTURE_3D` + `texImage3D()`，WebGL2 特性。 | **真机已确认支持**（WebGL2 ✅，3D 纹理 ✅）。当前 MP 暂将 LUT 设为 `null` 为产品选择；若需启用，在保证 WebGL2 的前提下传入 LUT 纹理即可。 |
| **LBS（线性混合蒙皮）** | 骨骼驱动 mesh，shader 为 GLSL 300 es。 | 在 WebGL2 下**正常支持**，无需降级。 |

**实现**：Canvas 适配器应只请求 `webgl2`，若获取失败则报错并提示升级微信或设备，不 fallback 到 `webgl`。
